# PWA, Organigramme, Documents, Self-service, Leave Workflow, and Notifications for WorkDays

This change adds six features in one batch: a PWA manifest with service worker for mobile installability, a hierarchical org chart backed by a `manager_id` column, a per-employee document storage module using base64, a self-service employee portal (simulated login), a leave request/approval workflow that auto-creates `year_calendar` entries on approval, and an in-app notification system with bell component and API. The approach leans on the existing client-side pattern (use client + `createClient()`) for pages and admin API routes for mutations that need service-role access. All six features ship as four new migrations (024-027), two new API routes, one helper lib, and eight new pages.

Watch for: notifications are fetched globally without any employee scoping, so every user sees all notifications for all employees (confirmed). The leave approval logic inserts `year_calendar` rows one at a time inside a loop with no transaction boundary, meaning a partial failure leaves the calendar in an inconsistent state (confirmed). Documents are stored as base64 in a TEXT column with no server-side size validation, relying entirely on client-side checks that can be bypassed (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The notification system has no concept of "current user." The bell component fetches the latest 10 notifications system-wide (`GET /api/notifications?limit=10`) and displays them all regardless of `employee_id`. In a multi-user context (even the simulated dropdown-based "login"), the self-service portal selects an employee but the notification bell shows everything. The API route's GET handler never filters by employee_id unless the caller explicitly passes it, and no caller does.

The leave approval flow in `PATCH /api/leave-requests` iterates from start to end date, inserting one `year_calendar` row per working day. Each insert is independent; if the fifth insert fails (duplicate, constraint violation), the first four remain and the request is still marked approved. There is no rollback path. The `approved_by` field is also never populated with a real value since the approvals page doesn't pass an approver identity.

Document storage uses Supabase's regular client (not admin) for inserts directly from the browser, which means RLS policies on `employee_documents` must allow public inserts, or uploads will silently fail. The 2 MB limit is enforced only in the browser; the table itself has no constraint. Base64 encoding inflates file size by ~33%, so the effective stored payload for a 2 MB file is ~2.7 MB per row.

The PWA service worker uses a network-first strategy with cache fallback. It caches every successful GET response indiscriminately, which means API responses (JSON data) will also land in the service worker cache and could serve stale data when the network recovers.

The organigramme tree-building logic is clean: it builds a map, resolves parent pointers, and collapses orphans into roots. The only gap is that an employee whose `manager_id` references an inactive employee will appear as a root node rather than under their (invisible) manager, which may surprise users.

The self-service portal aggregates salary, RTT, vacation balance, absences, and documents into a single page with many sequential Supabase queries. There's no parallelism beyond the initial employee list load, so loading latency will grow with the number of data sources.

<summary>Issues (7)</summary>

1. **Notifications not scoped to employee** — `GET /api/notifications` and the bell component fetch all notifications without filtering by `employee_id`. Add an `employee_id` query param and use it in the bell (based on selected employee or a context).
2. **No transactional insert in leave approval** — `year_calendar` rows are inserted one by one; a mid-loop failure leaves partial entries with no rollback. Wrap in a Supabase RPC or collect rows and use a single batch insert.
3. **`approved_by` never set** — The approvals page sends `{ id, action: "approve" }` without an `approved_by` value. The API defaults it to `null`. Pass the approving employee's ID.
4. **No server-side document size enforcement** — The 2 MB limit is browser-only. A direct POST to Supabase bypasses it. Add a CHECK constraint or validate in an API route.
5. **Service worker caches API responses** — The SW intercepts all GET requests including `/api/*` and caches their JSON responses. Exclude API paths from caching.
6. **Client-side `createNotification` fails silently on approval** — If the notification POST fails after a successful approval, the user gets no feedback that the notification wasn't sent. Consider making notification creation non-blocking but logged.
7. **Inactive-manager orphan in organigramme** — Employees whose `manager_id` points to an inactive (filtered-out) employee appear as root nodes. Either include inactive managers as ghost nodes or reassign children.

## Notification scoping gap

The `GET` handler in `/api/notifications/route.ts` accepts `limit` and `is_read` parameters but never accepts or uses `employee_id`:

```typescript
let query = supabase
  .from("notifications")
  .select("*")
  .order("created_at", { ascending: false })
  .limit(limit);
```

The bell component calls `fetch("/api/notifications?limit=10")` unconditionally. In the current app there's no auth, but even with the simulated employee selector, the bell doesn't know which employee is "logged in" because it's rendered in `layout.tsx` outside any employee-selection context. Every notification created for any employee is visible in the dropdown. This defeats the purpose of employee-targeted notifications (the `createNotification` helper explicitly takes an `employeeId` parameter).

The fix requires either a global context/state for "current employee" that the bell can read, or passing employee_id via a query parameter sourced from a cookie or URL state.

## Leave approval: non-atomic calendar insertion

The approval handler in `/api/leave-requests/route.ts` loops over the date range:

```typescript
for (let d = new Date(start); d <= end; d.setDate(d.getDate() + 1)) {
  // ...skip weekends, holidays, zero-schedule...
  const { error: insertError } = await supabase
    .from("year_calendar")
    .insert(record);
  if (!insertError) {
    insertedDays.push(dateStr);
  }
}
```

If an insert fails (e.g., a unique constraint on `(employee_id, absence_date)` if the employee already has an entry for that day), the loop continues and the request still gets marked `approved` with `total_days` set to however many inserts succeeded. The response returns `{ success: true, days_inserted: N }` even if N is less than expected. There's no comparison against expected days and no transaction grouping.

Additionally, the `approved_by` field in the update:
```typescript
approved_by: approved_by || null,
```
is always `null` because the client (`handleApprove` in approvals/page.tsx) sends `{ id: request.id, action: "approve" }` without an `approved_by` field. This means the audit trail for who approved a request is always empty.

## Document storage: base64 in TEXT with no server-side guard

Documents are stored via `createClient()` (the anon/public Supabase client) directly from the browser:

```typescript
const { error } = await supabase.from("employee_documents").insert({
  employee_id: Number(employeeId),
  name: docName,
  file_type: file.type || null,
  file_size: file.size,
  file_base64: base64,
  // ...
});
```

The 2 MB check is `if (file.size > MAX_SIZE_BYTES)` in the browser. Nothing prevents a crafted request from inserting a larger payload directly to Supabase (if RLS allows it) or through any future API route. The base64 encoding adds ~33% overhead, so a "2 MB" file becomes ~2.7 MB in the database. For a table that could accumulate hundreds of documents per employee, this will create significant database bloat and slow queries that `SELECT *` on the table (which the documents page does).

The migration also lacks an index on `employee_id`, so listing documents for a single employee will table-scan as the data grows.

## Service worker caches API responses

The service worker in `public/sw.js` uses a fetch handler that caches every GET response:

```javascript
self.addEventListener('fetch', (event) => {
  if (event.request.method !== 'GET') return;
  event.respondWith(
    fetch(event.request).then((response) => {
      const responseClone = response.clone();
      caches.open(CACHE_NAME).then((cache) => {
        cache.put(event.request, responseClone);
      });
      return response;
    }).catch(() => {
      return caches.match(event.request).then((cached) => {
        return cached || caches.match('/');
      });
    })
  );
});
```

This means every call to `/api/notifications`, `/api/leave-requests`, or any Supabase REST call routed through the Next.js server will be cached. When the network drops and returns, the user may see stale notification counts or old leave request lists from the cache. API routes should be excluded (e.g., `if (event.request.url.includes('/api/')) return;`).

## Self-service sequential queries

`loadEmployeeData` in the self-service page makes 8 sequential Supabase calls (vacation rights, vacation used, timesheet, RTT entitlements, absences, salary scales, indexations, documents). These could be parallelized with `Promise.all` since they have no data dependencies between them (the salary calculation depends on scale data, but that's a computation after fetch, not a query dependency). On a slow connection, this turns into perceptible latency.
