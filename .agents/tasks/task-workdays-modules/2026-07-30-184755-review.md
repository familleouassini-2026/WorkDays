# HR modules: Employee Edit, Absences, Remuneration, Dynamic Dashboard

This change adds four functional modules to the WorkDays HR application: an employee edit form at `/employees/[id]/edit`, a full absences module (booking wizard, calendar view, vacation balances), a remuneration module (salary scales, indexation history, salary simulator), and a dynamic dashboard fetching real Supabase data. All pages follow the existing client-side data fetching pattern (`'use client'` + `createClient()` + `useEffect`) and render UI in French. The implementation is roughly 4,900 lines of new code across 11 source files.

Watch for: Non-atomic two-table write in the absence booking wizard leaves orphaned `holiday_selections` rows on partial failure (confirmed). The seniority calculation in the salary simulator double-counts granted years when `granted_seniority_date` is used (confirmed). The dashboard exposes the Supabase anon key to unauthenticated clients with no RLS enforcement visible in this diff (likely). Hardcoded year lists in filter dropdowns will silently exclude data outside the listed range (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The absence booking wizard inserts into two tables (`holiday_selections` then `year_calendar`) without a transaction, meaning a failure on the second insert orphans the first row. This is the most consequential correctness issue because it corrupts balance calculations downstream.

The salary simulator's seniority logic uses `granted_seniority_date` as the reference date for year-difference calculation and then *adds* `granted_seniority` on top. If the organisation's convention is that `granted_seniority_date` already encodes the granted bonus (i.e., it's an adjusted start date), this double-counts. If `granted_seniority` is truly additive years beyond what the date implies, it's correct, but the two fields have overlapping semantics that should be documented or guarded.

Every page creates a fresh Supabase browser client on mount and queries without visible Row-Level Security policies in this diff. The anon key is embedded in the client bundle. If RLS is not configured on the backing tables, any authenticated or anonymous user can read and write all employee, salary, and absence data.

All filter dropdowns for year selection use hardcoded arrays (`[2025, 2024, 2023, 2022]`). By 2026 or for data before 2022, the UI silently hides matching records with no indication to the user.

## Non-atomic writes in the absence booking wizard

The `/absences/new` page performs a two-step insert: first into `holiday_selections`, then into `year_calendar`. If the calendar insert fails (constraint violation, network error, RLS denial), the selection row persists with no calendar entries linked to it. The balances page aggregates used time from `year_calendar`, not `holiday_selections`, so the balance will appear correct but the pending-requests count on the dashboard will include an orphaned request that can't be approved or cancelled.

```typescript
const { data: selectionData, error: selectionError } = await supabase
  .from("holiday_selections")
  .insert([...])
  .select("id")
  .single();

// If this fails, selectionData is already committed
const { error: calError } = await supabase
  .from("year_calendar")
  .insert(calendarEntries);
```

The fix is either a Supabase RPC wrapping both inserts in a Postgres transaction, or a compensating delete of the `holiday_selections` row if the calendar insert fails.

## Seniority calculation semantics in the simulator

```typescript
function calculateSeniorityYears(employee: Employee): number {
  const referenceDate = employee.granted_seniority_date
    ? new Date(employee.granted_seniority_date)
    : employee.date_of_hire
    ? new Date(employee.date_of_hire)
    : null;
  // ...
  const grantedYears = employee.granted_seniority || 0;
  return Math.max(0, years + grantedYears);
}
```

When `granted_seniority_date` is set, the function uses it as the anchor and *also* adds `granted_seniority`. Belgian HR convention typically treats `granted_seniority_date` as "pretend the employee started on this date" — an already-adjusted anchor. Adding extra years on top inflates the seniority, pulling a higher salary scale than warranted. The salary impact of a single erroneous scale step can be hundreds of euros per month.

## Timezone issues with date arithmetic

Two locations construct ISO date strings from `new Date()` objects:

In the dashboard:
```typescript
const today = new Date().toISOString().split("T")[0];
```

In the booking wizard's day-iteration loop:
```typescript
absence_date: current.toISOString().split("T")[0],
```

Belgium is UTC+1 (winter) or UTC+2 (summer). A `new Date("2025-07-15")` in a Belgian browser creates midnight local time, which is `2025-07-14T22:00:00Z` in summer. Calling `.toISOString()` on that yields `"2025-07-14"`, not `"2025-07-15"`. The dashboard may miscount today's absences, and the booking wizard may generate calendar entries for wrong dates.

Safe alternative:
```typescript
const pad = (n: number) => String(n).padStart(2, "0");
const dateStr = `${d.getFullYear()}-${pad(d.getMonth()+1)}-${pad(d.getDate())}`;
```

## Hardcoded year selectors

The balances page offers `[2025, 2024, 2023, 2022]` and the absences list page offers `[2025, 2024, 2023, 2022, 2021]`. These are static arrays that won't auto-expand. An administrator querying 2026 data after January 1st 2026 will find no year option available. Derive from `new Date().getFullYear()` and generate a range dynamically.

## Dashboard mixes live and hardcoded data

The left panel ("Absences recentes") fetches real data. The right panel ("Evenements a venir") renders hardcoded placeholder events — fictional employee names, fixed dates. There's no visual distinction (no "beta" badge, no "exemple" label). A user unfamiliar with the development status will treat these as real upcoming events.

## Supabase client instantiation pattern inconsistency

The employee edit form and booking wizard call `createClient()` in the component body (outside `useEffect`), creating a new reference on every render. The dashboard and calendar pages call it inside the effect. The body-level pattern is fragile: if a future change adds the `supabase` const to a `useEffect` dependency array, it will infinite-loop. Standardize on calling `createClient()` inside the effect or memoizing with `useMemo`.
