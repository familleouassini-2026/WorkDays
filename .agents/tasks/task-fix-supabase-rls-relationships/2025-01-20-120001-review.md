# Fix silent query failures: RLS anon policies and FK disambiguation for PostgREST (v2)

The app uses the Supabase anon key without user authentication, so relational `.select()` queries with joins were failing silently due to PostgREST being unable to resolve ambiguous FK paths. This change adds `anon` role RLS policies for all 10 RLS-enabled tables, comments ambiguous FK constraints for PostgREST disambiguation, and updates three app pages to use `!column_name` hint syntax. The dashboard's column bugs (`date` → `absence_date`, `label` → `description`) are both fixed.

Watch for: The FK constraint comments assume Postgres auto-naming conventions which are correct for Supabase-managed schemas but would break if constraints were manually named differently (likely correct, non-blocking).

**Verdict**: APPROVED

## High-level view

The v1 review raised three issues. Issue #1 (anon write policies) is confirmed intentional. Issue #2 (`absence_codes.label` → `description`) has been fixed — the TypeScript interface, query, and template all consistently reference `description` now. Issue #3 (constraint naming assumption) remains a non-blocking verification note.

The error handling asymmetry between the employees list (visible error banner) and the employee detail page (console-only logging, no user feedback) is the only new observation worth noting.

## Error handling asymmetry in employee pages

The employees list page renders a user-facing error banner (`fetchError` state + red alert div) when the query fails. The employee detail page only logs to console and resolves the loading state with no data — the user sees a blank page with no indication of failure.

This isn't a regression (the detail page never had error UX), but it's an inconsistency introduced by this PR: one page got proper error feedback while its sibling did not. A future pass could add an error state to the detail page for parity.
