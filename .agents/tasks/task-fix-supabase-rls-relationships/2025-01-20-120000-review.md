# Fix silent query failures: RLS anon policies and FK disambiguation for PostgREST

The app uses the Supabase anon key without requiring user authentication, which meant relational `.select()` queries with joins silently returned `null` for embedded resources. This change adds explicit `anon` role RLS policies for all 10 RLS-enabled tables, comments ambiguous FK constraints so PostgREST can resolve join hints, and updates three app pages to use the `!fk_column` hint syntax in their `.select()` calls. The column name bug (`date` instead of `absence_date` in the dashboard) is fixed along the way.

Watch for: The anon policies grant unrestricted INSERT/UPDATE/DELETE to unauthenticated users (confirmed). The dashboard query still references a non-existent `label` column on `absence_codes` (confirmed, pre-existing but carried forward). The FK constraint comments assume Postgres auto-naming conventions (`tablename_column_fkey`) which may not match if the database was created with a different naming scheme (likely correct for Supabase-managed schemas but worth verifying).

**Verdict**: NEEDS_CHANGES

## High-level view

The RLS fix adds 20 policies (SELECT + ALL per table) for the `anon` role. However, the existing "authenticated" policies already omit a `TO` clause, which in PostgreSQL means they apply to `PUBLIC` (all roles including `anon`). The real unblocking fix is the FK disambiguation — PostgREST was unable to resolve ambiguous relationships, not blocked by RLS. The anon policies are redundant but harmless; however, the `FOR ALL` anon policy opens full write access to every table for any unauthenticated API caller with the anon key.

The FK disambiguation migration uses `COMMENT ON CONSTRAINT` to annotate the circular references (org representative, location responsible, sector manager) and the forward references from employees and year_calendar. The app code then uses PostgREST hint syntax (`sectors!sector_id`, `locations!location_id`, etc.) to select the correct join path.

The dashboard page fixes the column name `date` → `absence_date` to match the actual schema, and adds FK hints for the year_calendar joins. The `absence_codes(code, label)` select references a column `label` that doesn't exist in the schema (it's `description`). This was pre-existing but the PR touched this exact query and had the opportunity to fix it.

## Anon RLS policies: redundant and overly permissive

The existing policies in `schema.sql` are:

```sql
CREATE POLICY "Allow all for authenticated" ON employees FOR ALL USING (true);
```

These lack a `TO` clause, which means they apply to the `PUBLIC` pseudo-role — all roles, including `anon`. The silent query failures were therefore not caused by missing RLS policies; they were caused by PostgREST failing to resolve ambiguous FK relationships (multiple foreign keys between the same pair of tables).

The concern is that `"Allow anon all" FOR ALL TO anon USING (true) WITH CHECK (true)` explicitly grants INSERT, UPDATE, and DELETE access to unauthenticated API users. Anyone with the anon key (which is public in a Supabase project URL) can modify or delete all data. If the intent is read-only anon access, the `"Allow anon read" FOR SELECT` policy is sufficient and the `"Allow anon all"` policies should be removed.

## FK disambiguation via constraint comments

PostgREST uses `COMMENT ON CONSTRAINT` metadata to pick the correct join path when a table has multiple FKs pointing to the same target. The migration annotates:

- Circular refs: `fk_org_representative`, `fk_location_responsible`, `fk_sector_manager` (named in schema via `ALTER TABLE ... ADD CONSTRAINT`)
- Forward refs: `employees_sector_id_fkey`, `employees_location_id_fkey`, `year_calendar_employee_id_fkey`, `year_calendar_absence_code_id_fkey` (auto-named from inline `REFERENCES`)

The app code uses the column-name hint syntax (`sectors!sector_id`, `employees!employee_id`) rather than the constraint-name hint syntax (`sectors!employees_sector_id_fkey`). Both are valid PostgREST patterns. The column-name style works as long as PostgREST can find exactly one FK on that column — which it can once the comments disambiguate the reverse paths. Worth noting: if a future migration adds a second FK on the same column, the column-name hint will become ambiguous again.

## Dashboard `absence_codes.label` ghost column

The dashboard's `RecentAbsence` interface declares `absence_codes: { code: string; label: string }` and the query selects `absence_codes!absence_code_id(code, label)`. The `absence_codes` table has columns `code` and `description` — no `label`. PostgREST will return `null` for the non-existent column or error depending on version. The template renders `{absence.absence_codes?.label}` which will display nothing.

This bug pre-existed in main, but the PR modified this exact query (adding FK hints, fixing `date` → `absence_date`). The fix is trivial: change `label` to `description` in both the select string and the TypeScript interface.
