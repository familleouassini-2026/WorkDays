# Report Builder Phase 2: calculated columns, smart filters, enhanced preview and PDF

This change adds five capabilities to the existing report builder: template duplication with auto-naming, five virtual calculated columns (seniority, indexed salary, age, work time %, seniority considered), smart filter widgets that adapt to field type (date range, sector dropdown, boolean, status, year), two SQL RPC aggregation functions, and an enhanced preview/PDF export with full row counts, grouped views with colored headers, subtotals, grand totals, and print headers/footers. The approach is entirely client-side for calculations — data is fetched via the existing `executeReport` engine and enriched in a second pass by `applyCalculatedColumns`. The RPC functions provide server-side aggregation as an optional optimization with automatic null-fallback.

Watch for:
- **Missing schema columns for calculated column dependencies** (confirmed): `granted_seniority` and `granted_seniority_date` are referenced in requiredFields metadata but not declared in the employees table's `columns` array in schema-metadata.ts. The data still arrives because the engine uses `select(*)`, but the wizard's Step 2 column picker cannot display or select these fields, making it impossible for a user to include them as visible columns or realize they're needed.
- **Date-range filter operator override** (confirmed): when a user selects a date field and sets the operator to anything other than the auto-inferred range (e.g., "eq" or "like"), the widget still renders two date inputs and produces gte/lte pairs regardless of the chosen operator.
- **Print header/footer using position:fixed** (likely): CSS `position: fixed` inside `@media print` only produces a single overlay on most browsers (Chrome, Firefox), not a per-page repeating header. Only `thead { display: table-header-group }` or `@page` margin boxes (not widely supported) reliably repeat content.

**Verdict**: NEEDS_CHANGES

## High-level view

Three computed columns depend on employee fields (`granted_seniority`, `granted_seniority_date`) that aren't declared in the schema metadata column list. The UI can't help users understand or select those dependencies, and a future refactor to select only declared columns would silently break the calculations.

The smart filters in Step 3 select their widget type based on the field name, but ignore the user's chosen operator. A date-range widget always emits gte+lte filter pairs even when the user explicitly chose "eq" — the operator dropdown becomes meaningless for date fields.

The SQL RPC `get_salary_overview` computes seniority differently than the client-side logic (ignoring `granted_seniority` bonus years), creating a divergence in base salary lookup between the two paths. The `executeRpcAggregation` helper is exported but never called — dead code for now.

The PDF print strategy uses `position: fixed` elements for repeating headers/footers, which in practice overlap content on pages beyond the first rather than creating per-page repeating headers. The body padding (30px) only affects page 1 layout.

The duplicate flow sets the name to "Copie de [original]" and redirects via `window.location.href` (full page reload) rather than Next.js router.

## Calculated columns: dependency gap in schema metadata

The `calculatedColumns` array in schema-metadata.ts declares `requiredFields: ["employees.granted_seniority", "employees.granted_seniority_date"]` for the seniority calculations, but the employees table's `columns` array has no corresponding entries. The computed columns work at runtime because `buildSupabaseQuery` selects `*` from the primary table, so PostgreSQL returns all columns. But the gap means:

- The "Colonnes calculees" section shows "Requiert: employees" without surfacing the specific field dependencies.
- If the query is ever refactored to select only declared columns, the calculations silently produce nulls.
- Users cannot include `granted_seniority` as a visible column in their report.

## Date-range filter widget ignores operator selection

In `buildConfig`:

```typescript
if (widgetType === "date_range" && f.value && f.valueTo) {
  mappedFilters.push({ field: f.field, op: "gte", value: f.value });
  mappedFilters.push({ field: f.field, op: "lte", value: f.valueTo });
}
```

The user's actual `f.op` is discarded. If a user selects "eq" and fills both date inputs, they still get a range filter. If they only fill `value` (no `valueTo`), the else-branch emits the user's chosen operator — creating behavioral inconsistency between "both fields filled" and "one field filled".

## Print header/footer strategy

```css
.print-header { position: fixed; top: 0; ... }
.print-footer { position: fixed; bottom: 0; ... }
body { padding-top: 30px; padding-bottom: 30px; }
```

In Chrome's print renderer, `position: fixed` elements appear on every page but overlap content on pages 2+ because `padding-top: 30px` doesn't apply per-page — it only affects the document flow once. The practical result on a 3-page report: headers/footers overlay the first data row on pages 2 and 3.

The `thead { display: table-header-group }` rule already in the CSS correctly repeats table column headers. A table-wrapper approach (title in a repeated `<thead>` row) would be more reliable for the report title.

## SQL RPC: seniority calculation divergence

The `get_salary_overview` function computes seniority as:

```sql
EXTRACT(YEAR FROM age(now(), e.date_of_hire))::INT AS seniority_years
```

This ignores `granted_seniority` and `granted_seniority_date` entirely. The client-side `calculateSeniorityYears` in calculations.ts adds `granted_seniority` to the time elapsed since `granted_seniority_date`. For any employee with granted seniority > 0, these two paths produce different values, which means the RPC looks up a different base_salary tier than the client would compute.

## Preview fetches all data for counting

`runPreview` calls `executeReport(config)` which fetches up to 5000 rows, stores the full array to read `.length`, then slices to 20 for display. Supabase supports `{ count: 'exact', head: true }` on queries to get the total count without transferring row data. A two-query approach (count + limited fetch) would reduce client memory pressure and network transfer for large reports.
