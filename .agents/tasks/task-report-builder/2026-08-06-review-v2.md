# Dynamic report builder with wizard UI and query engine (v2)

This change adds a complete report builder feature to WorkDays: a 6-step wizard for composing dynamic queries against 15 known tables, a query engine that translates saved JSONB configurations into Supabase calls with client-side flattening and grouping, and an execution page with PDF/CSV export. A `report_templates` table persists configurations. The reports listing page gains template CRUD. All six issues from the v1 review have been addressed: RLS policies, the 5000-row limit with a UI warning, correct `neq`/`not_null` filter mapping, the `updated_at` trigger, and UTF-8 BOM on CSV export.

Watch for: When a user selects `employees` as primary and `timesheets` as secondary (one-to-many FK direction), Supabase returns an array for the related table. The flattening logic only handles single-object relations — arrays are silently dropped, producing null columns with no error (confirmed). The query also includes unresolvable tables in the select string regardless of join availability, which will trigger PostgREST errors for table pairs with no FK path (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The query engine assumes every related table embeds as a single object (many-to-one direction). But several FK relationships in the schema point *from* child tables toward `employees` or `sectors` (timesheets, year_calendar, vacation_rights, seniority_scales, employee_indexations, sector_indexations). When one of these is the primary table and a parent table is secondary, embedding works. When `employees` is primary and `timesheets` is secondary, PostgREST returns an array. The flatten code checks `!Array.isArray(nested)` and skips it, so all timesheet columns come back null. No error is surfaced to the user.

The `buildSupabaseQuery` function includes every related table in the select string even when no valid join exists between it and the primary. PostgREST will reject the request with a "could not find a relationship" error. The wizard surfaces a warning about unlinked tables, but the engine doesn't guard against actually executing the broken query.

Client-side filters for related tables compare values without type coercion — numeric filter values remain strings through the pipeline, causing JavaScript comparison operators to use string ordering for multi-digit numbers.

<details>
<summary>Issues (4)</summary>

1. **One-to-many relations silently produce null columns** — When the FK direction causes Supabase to return an array (e.g., `employees` primary + `timesheets` secondary), the flatten code skips the array and fills all related columns with nothing. Either detect the array case and fan out into multiple rows (or take the first element with a warning), or prevent the user from selecting table combinations that produce arrays by checking FK direction in `resolveJoins`.
2. **Unresolvable tables still included in select** — `buildSupabaseQuery` adds `relatedTable(*)` for every secondary table regardless of whether a join was resolved. If two tables have no FK path, PostgREST returns an error. Guard the select: skip tables that have no matching entry in `config.joins`, or throw before execution when the join array is incomplete.
3. **Client-side numeric filter comparison uses string values** — Filter values pass through `buildConfig` as strings. Server-side filters work (PostgreSQL casts), but client-side filters on related tables do `(rowValue as number) > (filter.value as number)` where `filter.value` is a string. Parse numeric filter values to `Number()` before comparison.
4. **Description never saved** — The builder's `handleSave` payload is `{ name, config }`. The `report_templates.description` column is always null. Add a description input to the export step or derive it from config metadata.

## One-to-many embedding produces silent data loss

The flattening logic in `executeReport` (lines 213–232 of `report-engine.ts`) handles two cases for each related table:

```typescript
if (nested && typeof nested === "object" && !Array.isArray(nested)) {
  // flatten single object → works for many-to-one
} else if (nested === null) {
  // set all fields to null → works for left-join miss
}
// implicit: if nested is an array → skip entirely
```

PostgREST returns an array when the FK points *from* the related table *to* the primary (one-to-many). This happens for any report where `employees` is primary and a child table like `timesheets`, `year_calendar`, `vacation_rights`, or `employee_indexations` is secondary — all of which have `employee_id` FK pointing toward `employees.id`.

The user sees a table with correct primary-table columns but dashes/nulls for every related column, with no indication that the data was dropped rather than absent. The 5000-row limit makes this less catastrophic (no memory explosion from array fan-out), but the behavior is still incorrect and confusing.

Fix options:
- Check FK direction in `resolveJoins` and only allow embedding in the direction that produces a single object (child → parent).
- If the user selects the "wrong" direction, swap primary/secondary or fan out rows (one per array element).
- At minimum, detect the array case in the flatten loop and surface a user-facing error: "La table X retourne plusieurs enregistrements par ligne. Utilisez-la comme table principale."

## Unresolvable table pairs execute broken queries

In `buildSupabaseQuery`, both branches of the join-check produce identical output:

```typescript
if (joinDef) {
  selectParts.push(`${relatedTable}(*)`);
} else {
  // "Attempt to include without explicit join (Supabase will use FK inference)"
  selectParts.push(`${relatedTable}(*)`);
}
```

When there is no FK between the primary and related table (e.g., `holidays` + `meetings`), PostgREST cannot infer a relationship and returns a 400 error: "Could not find a relationship between 'holidays' and 'meetings' in the schema cache." This propagates as a generic "Report query failed" error on the execution page.

The builder wizard does show an amber warning when `resolveJoins` returns an empty array for the selected tables, but nothing prevents the user from saving and executing that config. The engine should either refuse to build the query (throw with a descriptive message before hitting Supabase) or skip unresolvable tables from the select and warn the user that those columns were excluded.

## Client-side filter type coercion gap

All filter values are stored as strings in the builder's `FilterRow` interface and passed through `buildConfig` without type conversion. When the engine applies numeric comparisons (`gt`, `lt`, `gte`, `lte`) on the primary table, Supabase accepts string values and PostgreSQL handles the cast. But client-side filters on related tables compare `rowValue as number > filter.value as number` — where `filter.value` is actually a string. JavaScript's `>` operator on a number vs. string uses type coercion that works for simple cases but breaks for multi-digit comparisons where string ordering diverges from numeric ordering (e.g., `"9" > "10"` is true as strings). Convert filter values to `Number(filter.value)` before the comparison in the client-side filter loop.
