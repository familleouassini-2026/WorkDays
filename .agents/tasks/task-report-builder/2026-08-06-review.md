# Dynamic report builder with wizard UI and query engine

This change introduces a complete report builder feature: a 6-step wizard for composing dynamic queries against 15 known tables, a query engine that translates the configuration into Supabase calls with client-side flattening and grouping, and an execution page with PDF/CSV export. A new `report_templates` table persists configurations as JSONB. The reports listing page gains a "Nouveau rapport" button and a CRUD section for saved templates.

Watch for: The `report_templates` table has no RLS enabled and no policies, meaning any anonymous user can read, insert, update, and delete all templates (confirmed). The query engine fetches all matching rows without any row limit, which risks memory exhaustion on large tables like `year_calendar` (confirmed). The `neq` and `is_not_null` filter operators in the wizard are mapped incorrectly in `buildConfig` — both silently produce wrong semantics (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The migration creates the table but omits the RLS setup that every other table in this project has. Without it, the table is world-writable to anonymous Supabase clients, inconsistent with the project's established security posture.

The query engine uses Supabase's relational embedding (`table(*)`) for joins and flattens the nested response client-side. Filters and sorts on related tables are also applied client-side after the full fetch. Because there is no `.limit()` anywhere in the pipeline, a report on `year_calendar` (which accumulates rows for every absence day across all years) will pull the entire table into browser memory.

The wizard maps user-facing filter operators to the engine's `ReportFilter` type, but `neq` is mapped to `eq` with the same value (inverted semantic lost) and `is_not_null` is mapped to `{ op: "is", value: null }` — identical to `is_null`. Both are confirmed in `buildConfig()`.

The builder page is an 827-line component containing all six wizard steps, preview logic, and save logic with no extraction into sub-components. This doesn't block shipping but makes the file difficult to review and maintain.

<details>
<summary>Issues (6)</summary>

1. **Missing RLS on `report_templates`** — Add `ALTER TABLE report_templates ENABLE ROW LEVEL SECURITY` and create at minimum the same anon allow-all policies used on every other table in this project. Without this, Supabase blocks all access by default when RLS is enabled project-wide (or allows unrestricted access when it isn't — both are problems).
2. **Unbounded query fetch** — Add a sensible `.limit()` (e.g. 5000 rows) to the Supabase query in `executeReport`, and surface a warning in the UI when the limit is hit. Without it, a report on `year_calendar` with no filters will attempt to load tens of thousands of rows into memory.
3. **`neq` filter mapped as `eq`** — In `buildConfig()`, the `neq` case returns `{ op: "eq", value: f.value }`. It should use Supabase's `.neq()` (add `"neq"` to the `ReportFilter` op union) or apply client-side negation.
4. **`is_not_null` filter mapped identically to `is_null`** — Both produce `{ op: "is", value: null }`. The `is_not_null` case needs to use `.not("column", "is", null)` or a dedicated op.
5. **No `updated_at` trigger** — The migration defines `updated_at TIMESTAMPTZ DEFAULT NOW()` but no trigger updates it on modification. Template edits will keep the original timestamp.
6. **CSV export doesn't handle values containing the UTF-8 BOM or special separators** — Minor, but adding a UTF-8 BOM (`\uFEFF`) at the start of the CSV blob would ensure Excel opens it correctly with French characters.

## Missing RLS and table-level grants on `report_templates`

Every other table in this project follows the pattern: `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` followed by at least `CREATE POLICY "Allow anon read" ... FOR SELECT TO anon USING (true)` and a matching write policy. The `021-report-templates.sql` migration creates the table with no RLS and no grants. The practical impact depends on the Supabase project configuration: if RLS is enforced at the project level, anonymous clients get zero access to the table (silent failures on the listing page); if it isn't enforced, the table is unrestricted. Either way, the migration is incomplete relative to the project's own conventions.

```sql
-- What's missing (following patterns from migrations 002–005):
ALTER TABLE report_templates ENABLE ROW LEVEL SECURITY;
CREATE POLICY "Allow anon read report_templates"
  ON report_templates FOR SELECT TO anon USING (true);
CREATE POLICY "Allow anon all report_templates"
  ON report_templates FOR ALL TO anon USING (true) WITH CHECK (true);
```

## Unbounded data fetch in `executeReport`

The query built by `buildSupabaseQuery` has no `.limit()` call. The preview in the builder correctly slices to 20 rows client-side (`data.slice(0, 20)`), but the underlying fetch still retrieves the full result set. On the execution page (`/reports/[id]`), the full data is loaded without any cap. Supabase's default limit is 1000 rows per request (unless overridden in project settings or the client specifies otherwise), but the code does not explicitly handle pagination or communicate the truncation to the user. If the project's Supabase config raises this limit, memory exhaustion becomes a real risk for tables like `year_calendar` or `timesheets`.

## Filter mapping defects in `buildConfig()`

The `buildConfig` function in the builder page translates wizard-facing operators to engine-facing ones. Two cases are broken:

```typescript
// neq → becomes eq with same value (wrong)
if (f.op === "neq") {
  return { field: f.field, op: "eq" as const, value: f.value };
}

// is_not_null → becomes { op: "is", value: null } — same as is_null
if (f.op === "is_not_null") {
  return { field: f.field, op: "is" as const, value: null };
}
```

A user selecting "different" or "n'est pas vide" in the wizard will get the opposite of what they expect. The engine's `ReportFilter` type doesn't currently include a `neq` op or a `not_null` variant, so the fix requires extending both the type and the `buildSupabaseQuery` switch.

## Client-side filtering asymmetry

Filters on the primary table are pushed down to Supabase via query builder methods. Filters on related tables are applied client-side after the full fetch. This is a conscious design choice documented in code comments, but it means that a filter like "sector name = X" on a report rooted in `employees` doesn't reduce the Supabase response size — all employees are fetched, then filtered in the browser. Combined with the lack of a row limit, this amplifies the memory concern.

## Relational join limitations

The engine uses Supabase's embedding syntax (`relatedTable(*)`) which relies on PostgREST's FK inference. This works for direct FK relationships (employees → sectors) but won't handle multi-hop joins (e.g., `year_calendar` → `employees` → `sectors`). If a user selects `year_calendar` and `sectors` without also selecting `employees`, the join resolution will find no direct FK between them, the warning fires, but the query still attempts `sectors(*)` on `year_calendar` — which PostgREST will reject with an error. The `resolveJoins` function correctly warns, but `buildSupabaseQuery` still includes the unresolvable table in the select string regardless of whether a valid join was found (the `else` branch adds it anyway with a comment about "FK inference").

## No test coverage

The project has no test framework configured. The schema metadata, query engine logic (especially filter mapping, join resolution, and grouping), and config serialization round-trip are all untested. The filter mapping bugs above would be trivially caught by unit tests.
